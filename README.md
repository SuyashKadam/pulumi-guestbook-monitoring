# pulumi-guestbook-monitoring

This is the [Pulumi Kubernetes Guestbook example](https://github.com/pulumi/examples/tree/master/kubernetes-ts-guestbook)
(TypeScript) with Prometheus and Grafana added, so the app can actually be monitored. A single `pulumi up` deploys
the app, the monitoring stack, the scrape config and a Grafana dashboard.

I ran it on minikube (Docker driver) on Ubuntu under WSL2. It should work on any Linux box with minikube, and on a
cloud cluster with one config change (see [Running on a cloud cluster](#running-on-a-cloud-cluster)).

For a full walkthrough from a clean machine, see [SETUP.md](./SETUP.md).

## What gets deployed

`guestbook` namespace:
- redis-leader, redis-replica and 3 frontend pods. These are the same images as the upstream example.
- an exporter sidecar in every pod: `apache_exporter` in the frontend pods, `redis_exporter` in the Redis pods
- `frontend-metrics`, a ClusterIP service for the frontend exporters. The Redis services just get an extra `metrics` port.
- two ServiceMonitors, `guestbook-frontend` and `guestbook-backend`

`monitoring` namespace:
- the `kube-prometheus-stack` Helm chart (v92.0.0): Prometheus Operator, Prometheus, Grafana, kube-state-metrics and node-exporter
- a ConfigMap with the Guestbook dashboard, which Grafana picks up automatically

```
 browser / load-generator
          |
          v
 frontend x3 ----- apache_exporter :9117 --+
 redis-leader ---- redis_exporter  :9121 --+--> Prometheus --> Grafana
 redis-replica --- redis_exporter  :9121 --+        ^
                                                    |
 kubelet / cAdvisor (pod CPU + memory) -------------+
```

## How the monitoring works

The guestbook images don't expose any metrics, so I put an exporter next to each app container. The exporter talks
to the app over localhost inside the pod:

- **Frontend:** `apache_exporter` reads Apache's `mod_status` page and exposes `apache_accesses_total`, which is the request count,
  plus worker stats. A small ConfigMap mounted into `conf-enabled/` switches on `/server-status` and limits it to
  localhost, so it isn't reachable from outside the pod.
- **Backend:** `redis_exporter` reads `INFO` from Redis and exposes `redis_commands_processed_total`,
  `redis_connected_clients` and so on.
- **Resource usage:** CPU and memory per pod come from cAdvisor, which the chart already scrapes through the kubelet.

Each exporter port is published on a Service as a port named `metrics`, and those Services carry the label
`monitoring: enabled`. The two ServiceMonitors select those Services by tier and scrape `metrics` every 15s. That gives
5 targets in total: 3 frontend and 2 Redis.

A few things worth pointing out:

- `serviceMonitorSelectorNilUsesHelmValues: false` is set on Prometheus. Without it, the chart's Prometheus only
  picks up ServiceMonitors that carry its own `release` label, so the guestbook ones would be silently ignored.
- I used ServiceMonitors and not `prometheus.io/scrape` annotations, because the Prometheus Operator doesn't read those annotations.
- The ServiceMonitors depend on the Helm release, because the ServiceMonitor CRD only exists once the chart is installed.
- The frontend metrics go through their own ClusterIP service rather than the public frontend service.
- The Grafana admin password is generated by Pulumi (`random.RandomPassword`) and kept as a secret in the stack, so
  nothing is hard-coded in the repo.
- Alertmanager is disabled because alerting wasn't part of the task.

## Requirements checklist

- **Prometheus and Grafana deployed with Pulumi:** `monitoring.ts`, a Helm release of kube-prometheus-stack.
- **Prometheus scrapes the frontend and backend:** ServiceMonitors in `monitoring.ts`, plus exporters and metrics services in `guestbook.ts`.
- **Simple metrics:** request count (`apache_accesses_total`), Redis commands (`redis_commands_processed_total`), and pod CPU/memory.
- **Grafana exposed as NodePort/LoadBalancer:** NodePort on minikube (the default), LoadBalancer with `isMinikube=false`.
- **Grafana URL and admin credentials as Pulumi outputs:** `grafanaUrl`, `grafanaNodePort`, `grafanaAdminUser` and `grafanaAdminPassword` (secret).
- **Stretch goal, Grafana dashboard:** `dashboards/guestbook.json`, which shows up as "Guestbook Application".

## Prerequisites

- Linux with Docker and minikube (I used `--cpus=4 --memory=6144`)
- kubectl
- Pulumi CLI v3
- Node.js 20 or newer. Ubuntu's own `nodejs` package is too old: the Pulumi SDK fails with
  `SyntaxError: Unexpected token '.'`. Install Node from NodeSource instead (see SETUP.md).

## Deploy

```bash
minikube start --driver=docker --cpus=4 --memory=6144   # add --force if you're root

git clone https://github.com/SuyashKadam/pulumi-guestbook-monitoring.git
cd pulumi-guestbook-monitoring
npm install

pulumi login --local
export PULUMI_CONFIG_PASSPHRASE="pick-something"
pulumi stack init dev
pulumi up
```

The first `pulumi up` takes a few minutes, mostly pulling images and waiting for the chart to come up.

## Grafana URL and login

```bash
pulumi stack output grafanaUrl                            # http://localhost:3000
pulumi stack output grafanaAdminUser                      # admin
pulumi stack output grafanaAdminPassword --show-secrets
```

Grafana is exposed as a NodePort service (`kubectl -n monitoring get svc monitoring-grafana` shows `TYPE NodePort`).
The node port is in the `grafanaNodePort` output, so the direct NodePort URL is:

```bash
echo "http://$(minikube ip):$(pulumi stack output grafanaNodePort)"
minikube service -n monitoring monitoring-grafana --url    # same thing, worked out by minikube
```

That URL works from the Linux host. With the Docker driver on WSL2, the minikube IP isn't reachable from a Windows
browser, so I mostly used a port-forward instead. The command is also in the `grafanaPortForward` output:

```bash
kubectl -n monitoring port-forward svc/monitoring-grafana 3000:80
```

Then open http://localhost:3000 (the `grafanaUrl` output) and log in as `admin` with the password above. The password is different for every
deployment, so it's not written down anywhere in this repo.

The guestbook itself works the same way: run `kubectl -n guestbook port-forward svc/frontend 8080:80`, then go to http://localhost:8080.

## Checking that Prometheus scrapes the guestbook

Generate some traffic first. This loop runs inside the cluster and calls the guestbook about 5 times a second:

```bash
kubectl -n guestbook run load-generator --rm -it --restart=Never --image=curlimages/curl -- \
  sh -c "while true; do curl -s -o /dev/null -G http://frontend/guestbook.php -d cmd=get -d key=messages; sleep 0.2; done"
```

Check that the pods and ServiceMonitors are there. Every guestbook pod should be `2/2`, the app plus its exporter:

```bash
kubectl -n guestbook get pods
kubectl -n guestbook get servicemonitors
kubectl -n guestbook get svc -l monitoring=enabled
```

Port-forward Prometheus:

```bash
kubectl -n monitoring port-forward svc/monitoring-kube-prometheus-prometheus 9090:9090
```

On http://localhost:9090/targets, filter on `guestbook`. You should see:

```
serviceMonitor/guestbook/guestbook-frontend/0   3/3 up
serviceMonitor/guestbook/guestbook-backend/0    2/2 up
```

The same check from the API:

```bash
curl -s localhost:9090/api/v1/targets \
  | jq -r '.data.activeTargets[] | select(.labels.namespace=="guestbook") | "\(.labels.service) \(.labels.pod) \(.health)"'
```

Some queries to try in the Prometheus UI or in Grafana Explore:

```promql
up{namespace="guestbook"}                                                         # 5 series, all 1
sum(rate(apache_accesses_total{namespace="guestbook"}[1m]))                       # requests/s
sum by (service) (rate(redis_commands_processed_total{namespace="guestbook"}[1m])) # redis ops/s
sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="guestbook",container!=""}[2m]))
sum by (pod) (container_memory_working_set_bytes{namespace="guestbook",container!=""})
```

If you stop the load generator, the request rate drops within a minute. That's an easy way to see the numbers are live.

You can also read an exporter directly:

```bash
kubectl -n guestbook port-forward svc/frontend-metrics 9117:9117 &
curl -s localhost:9117/metrics | grep -E '^apache_(up|accesses_total)'
```

## Dashboard

In Grafana, go to Dashboards and open **Guestbook Application**. It has these panels:
- target health per service, and total requests
- frontend request rate per pod, and busy Apache workers
- Redis commands/s and connected clients
- CPU and memory per pod

There's no error-rate panel. Apache's status page doesn't break requests down by status code, so I stuck to request
rate and resource usage.

## Running on a cloud cluster

```bash
pulumi config set isMinikube false
pulumi up
```

With that set, Grafana and the frontend get `LoadBalancer` services, and `grafanaUrl` becomes the load balancer
address. That's an IP on GKE/AKS, or a hostname on EKS.

## Known quirks

- Every scrape of `/server-status` counts as one Apache request, so an idle frontend shows a small baseline of about
  0.07 req/s per pod.
- `redis` and `pulumi/guestbook-*` come from Docker Hub, which rate-limits anonymous pulls. If pods sit in
  `ImagePullBackOff` with a 429 error, wait a bit and run `pulumi up` again. The exporters are pulled from quay.io.
- On minikube I turned off node-exporter's host root filesystem mount. It can fail to start on Docker-based nodes,
  and nothing here needs it.

## Cleanup

```bash
pulumi destroy
pulumi stack rm dev
minikube delete
```
