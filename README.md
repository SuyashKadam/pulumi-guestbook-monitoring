# Guestbook on Kubernetes with Prometheus and Grafana (Pulumi, TypeScript)

This project takes the [Pulumi Kubernetes Guestbook example](https://github.com/pulumi/examples/tree/master/kubernetes-ts-guestbook)
and adds monitoring to it. One `pulumi up` deploys:

1. **The Guestbook app**: a Redis leader, a Redis replica and 3 PHP/Apache frontend pods (same images as the original example).
2. **Prometheus and Grafana**, installed with the `kube-prometheus-stack` Helm chart through Pulumi.
3. **Metrics for every Guestbook tier**, plus two **ServiceMonitors** that tell Prometheus to scrape them.
4. **Grafana exposed as a NodePort** on minikube/kind (the default), or as a **LoadBalancer** on a cloud cluster (`isMinikube=false`).
5. **Stack outputs** with the Grafana URL and admin credentials.
6. **A "Guestbook Application" Grafana dashboard** (the stretch goal). It shows request rates, Redis load, target health and pod CPU/memory.

> **First time running this?** Follow [EXECUTION-GUIDE.md](./EXECUTION-GUIDE.md). It's a step-by-step minikube (free, local) walkthrough with checkpoints.

## Architecture

```
                         ┌──────────────────────── namespace: guestbook ────────────────────────┐
  user ──HTTP──► Service "frontend" (LoadBalancer :80)                                          │
                 │   └─► frontend pod x3  [ apache+php :80 ]──localhost──►[ apache-exporter :9117 ]
                 │                                                                 ▲            │
                 │   Service "frontend-metrics" (ClusterIP :9117, label monitoring=enabled) ─┘  │
                 │                                                                              │
                 │   redis-leader pod   [ redis :6379 ]──localhost──►[ redis-exporter :9121 ]    │
                 │   redis-replica pod  [ redis :6379 ]──localhost──►[ redis-exporter :9121 ]    │
                 │   Services "redis-leader"/"redis-replica" (ClusterIP :6379 + metrics :9121)   │
                 │                                                                              │
                 │   ServiceMonitor guestbook-frontend  (tier=frontend, monitoring=enabled)      │
                 │   ServiceMonitor guestbook-backend   (tier=backend,  monitoring=enabled)      │
                 └─────────────────────────────────────┬────────────────────────────────────────┘
                                                       │ scrape every 15s on port "metrics"
                 ┌──────────────── namespace: monitoring (Helm: kube-prometheus-stack) ─────────┐
                 │  Prometheus Operator ─► Prometheus ◄── also scrapes kubelet/cAdvisor (pod CPU/mem)
                 │                            ▲                                                 │
                 │  Grafana (LoadBalancer :80) ── datasource "Prometheus"                       │
                 │     └─ dashboard sidecar loads ConfigMap "guestbook-dashboard"               │
                 └──────────────────────────────────────────────────────────────────────────┘
```
The diagram shows a cloud cluster. On minikube (the default) the frontend Service is `ClusterIP` and Grafana is `NodePort`,
and both are opened with `kubectl port-forward`.

### How it works

**1. Prometheus and Grafana (`monitoring.ts`)**
- `k8s.helm.v3.Release` installs the [kube-prometheus-stack](https://github.com/prometheus-community/helm-charts/tree/main/charts/kube-prometheus-stack)
  chart, pinned to version `92.0.0`, into the `monitoring` namespace. The chart installs the Prometheus Operator, Prometheus,
  Grafana, kube-state-metrics and node-exporter. It also preconfigures Prometheus to scrape the kubelet/cAdvisor,
  which is where pod CPU and memory usage come from.
- `serviceMonitorSelectorNilUsesHelmValues: false` matters here. By default the chart's Prometheus only picks up
  ServiceMonitors that carry the label `release: monitoring`. With this setting it picks up every ServiceMonitor, so
  the Guestbook ServiceMonitors are discovered.
- Alertmanager is turned off because alerting isn't part of this assignment.
- `grafana.service.type` is `NodePort` on minikube (the default, `isMinikube=true`) and `LoadBalancer` on a cloud cluster (`isMinikube=false`).
- Pulumi generates the Grafana admin password with `random.RandomPassword`, so nothing is hard-coded in Git. The
  password is stored encrypted in the Pulumi state as a **secret**.

**2. Exposing metrics from the Guestbook (`guestbook.ts`)**
The Guestbook images don't expose Prometheus metrics, so each pod gets a standard Prometheus *exporter* **sidecar**. The
sidecar shares the pod's network namespace and reads the app over `localhost`:

| Tier | Sidecar | What it reads | Main metrics |
|---|---|---|---|
| Frontend (Apache/PHP) | `apache-exporter` (port 9117) | Apache `mod_status` page `/server-status?auto` | `apache_accesses_total` (number of requests), `apache_workers`, `apache_sent_kilobytes_total`, `apache_up` |
| Backend (Redis leader + replica) | `redis-exporter` (port 9121) | Redis `INFO` | `redis_commands_processed_total` (number of commands), `redis_connected_clients`, `redis_memory_used_bytes`, `redis_up` |
| All pods | kubelet/cAdvisor (from the chart) | container runtime | `container_cpu_usage_seconds_total`, `container_memory_working_set_bytes` |

A small ConfigMap is mounted into Apache's `conf-enabled/`. It makes sure `mod_status` is loaded and serves
`/server-status`, restricted to requests from inside the pod (`Require local`). The exporter can read the page, but
users of the public site get `403`.

**3. Telling Prometheus what to scrape (ServiceMonitors)**
- Each metrics port is published as a Service port named `metrics`, and those Services carry the label `monitoring: enabled`:
  - `frontend-metrics` is a separate ClusterIP Service. Metrics are deliberately **not** put on the public frontend
    LoadBalancer.
  - `redis-leader` and `redis-replica` are already internal ClusterIP Services, so they just get a second port.
- `ServiceMonitor guestbook-frontend` selects `tier=frontend, monitoring=enabled`, and `ServiceMonitor guestbook-backend`
  selects `tier=backend, monitoring=enabled`. Both scrape port `metrics` every 15s.
- The Prometheus Operator watches the ServiceMonitors and generates the Prometheus scrape config for every pod behind
  those Services. That makes 5 targets: 3 frontend, 1 leader and 1 replica. Prometheus adds labels such as `namespace`, `service`
  and `pod` to every series.
- The ServiceMonitors use `dependsOn` on the Helm release, because the `ServiceMonitor` CRD only exists once the chart is installed.

> I used ServiceMonitors rather than `prometheus.io/scrape` annotations. The Prometheus Operator that
> kube-prometheus-stack runs ignores those annotations, so ServiceMonitors are the way that actually works with it.

**4. The Grafana dashboard (stretch goal)**
`dashboards/guestbook.json` goes into a ConfigMap labelled `grafana_dashboard: "1"`. The chart's Grafana sidecar
watches for that label and imports the dashboard automatically. It uses the chart's built-in Prometheus datasource
(uid `prometheus`).

**5. Outputs (`index.ts`)**
After deploy, Pulumi reads the Grafana Service back to get its LoadBalancer address. That address is an IP on GKE/AKS
and a hostname on EKS; both cases are handled. The stack then exports `grafanaUrl`, `grafanaAdminUser` and
`grafanaAdminPassword` (secret), plus `frontendUrl` and `prometheusService`.

## Prerequisites

- A Kubernetes cluster and a working `kubectl` context. This can be EKS/GKE/AKS, or **minikube/kind** for local runs.
  Give it at least 2 CPUs and 4 GB of RAM for the monitoring stack.
- [Pulumi CLI](https://www.pulumi.com/docs/install/) v3
- Node.js 20+ and npm (older versions such as Ubuntu's default Node 12 can't run the Pulumi SDK)

Pulumi uses your current kubeconfig context. Check it with `kubectl config current-context`.

## Deploy

```bash
git clone https://github.com/SuyashKadam/pulumi-guestbook-monitoring.git
cd pulumi-guestbook-monitoring
npm install

# Store state in Pulumi Cloud (`pulumi login`), or locally with no account needed:
pulumi login --local
export PULUMI_CONFIG_PASSPHRASE="choose-a-passphrase"   # needed with local login to encrypt secrets

pulumi stack init dev

# minikube is the default. Only on a cloud cluster (EKS/GKE/AKS) with LoadBalancer support:
# pulumi config set isMinikube false

pulumi up        # review the preview, choose "yes"; the first deploy takes ~3-6 minutes
```

## Grafana access URL and admin credentials

```bash
pulumi stack output grafanaUrl                        # minikube: http://localhost:3000 | cloud: http://<load-balancer>
pulumi stack output grafanaAdminUser                  # admin
pulumi stack output grafanaAdminPassword --show-secrets
```

Open `grafanaUrl` and log in with `admin` and the password above.

| | Value |
|---|---|
| Grafana URL | `pulumi stack output grafanaUrl` |
| Username | `admin` |
| Password | `pulumi stack output grafanaAdminPassword --show-secrets` (randomly generated per stack, stored as an encrypted Pulumi secret) |

**On minikube (the default)** there's no external load balancer, so first run the command printed in the
`grafanaPortForward` output, then open `http://localhost:3000`. Leave that terminal open while you use Grafana.
```bash
kubectl -n monitoring port-forward svc/monitoring-grafana 3000:80
```
The Guestbook UI works the same way through the `frontendPortForward` output: `kubectl -n guestbook port-forward svc/frontend 8080:80`, then `http://localhost:8080`.

## Generate some traffic

Open the Guestbook (`pulumi stack output frontendUrl`) and submit a few messages. You can also generate steady load
from inside the cluster (this works on any cluster, including minikube):

```bash
kubectl -n guestbook run load-generator --rm -it --restart=Never --image=curlimages/curl -- sh -c "while true; do curl -s -o /dev/null -G http://frontend/guestbook.php -d cmd=get -d key=messages; sleep 0.2; done"
# Ctrl+C to stop (the pod is removed automatically)
```

Every `guestbook.php` call increases Apache's request counter and runs a Redis command.

## Verify that Prometheus is scraping the Guestbook

**1. The ServiceMonitors and metrics Services exist**
```bash
kubectl -n guestbook get servicemonitors
# guestbook-backend, guestbook-frontend
kubectl -n guestbook get svc -l monitoring=enabled
# frontend-metrics, redis-leader, redis-replica
kubectl -n guestbook get pods
# every pod shows READY 2/2 (app + exporter sidecar)
```

**2. Open the Prometheus UI**
```bash
kubectl -n monitoring port-forward svc/monitoring-kube-prometheus-prometheus 9090:9090
```
Go to <http://localhost:9090/targets> and search for `guestbook`. You should see:
- `serviceMonitor/guestbook/guestbook-frontend/0`: **3/3 up** (one per frontend pod)
- `serviceMonitor/guestbook/guestbook-backend/0`: **2/2 up** (redis-leader and redis-replica)

**3. Check from the command line (with the port-forward above running)**
```bash
curl -s localhost:9090/api/v1/targets | \
  jq -r '.data.activeTargets[] | select(.labels.namespace=="guestbook") | "\(.labels.service)\t\(.labels.pod)\t\(.health)"'
# frontend-metrics  frontend-xxxx       up   (x3)
# redis-leader      redis-leader-xxxx   up
# redis-replica     redis-replica-xxxx  up
```

**4. Query the metrics** in <http://localhost:9090/query> (`/graph` on older Prometheus versions; or Grafana → Explore):

| Question | PromQL |
|---|---|
| Are all targets healthy? (expect 5 series = 1) | `up{namespace="guestbook"}` |
| Frontend requests per second | `sum(rate(apache_accesses_total{namespace="guestbook"}[1m]))` |
| Total frontend requests | `sum(apache_accesses_total{namespace="guestbook"})` |
| Redis commands per second | `sum by (service) (rate(redis_commands_processed_total{namespace="guestbook"}[1m]))` |
| Pod CPU usage | `sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="guestbook",container!=""}[2m]))` |
| Pod memory usage | `sum by (pod) (container_memory_working_set_bytes{namespace="guestbook",container!=""})` |

Run the load generator and you'll see the request and command rates go up.

**5. (Optional) Read an exporter directly**
```bash
kubectl -n guestbook port-forward svc/frontend-metrics 9117:9117 &
curl -s localhost:9117/metrics | grep -E '^apache_(up|accesses_total)'
```

## Grafana dashboard (stretch goal)

In Grafana, go to **Dashboards → Guestbook Application**. It has these sections:
- **Health**: up/down per Guestbook metrics Service, and total requests served.
- **Frontend (Apache)**: request rate per pod and busy workers.
- **Backend (Redis)**: commands per second for leader and replica, and connected clients.
- **Pod resource usage**: CPU and memory per Guestbook pod.

The chart's built-in dashboards (for example *Kubernetes / Compute Resources / Namespace (Pods)* → namespace `guestbook`)
work as well.

> Note: each Prometheus scrape of `/server-status` counts as one Apache request, so an idle frontend shows a baseline
> of about 0.07 req/s per pod (1 request every 15s).

## Clean up

```bash
pulumi destroy
pulumi stack rm dev
```
Destroying removes the cloud LoadBalancers that were created for the frontend and Grafana.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `pulumi up` waits a long time on `kube-prometheus-stack` on minikube/kind | Make sure `isMinikube` isn't set to `false` (`pulumi config`), because a LoadBalancer never gets an address there. |
| Target `down` in Prometheus | Run `kubectl -n guestbook logs <pod> -c apache-exporter` or `-c redis-exporter`. |
| Images fail with `ImagePullBackOff` / `429 Too Many Requests` | You hit the Docker Hub pull limit for `redis` / `pulumi/*`. Wait, or log the cluster in to Docker Hub. The exporter images come from quay.io. |
| No data in the dashboard | Check the targets first (step 2 above), then generate traffic. |
